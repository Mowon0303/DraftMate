## F1. 「我方结尾」也能给建议:追加/接话(follow-up)

**状态**:💡 想法已记录,设计待拍板(未开工)

### 背景 / 痛点
真人聊天里,自己发完一条之后,常常还会**追加**一句(补充、接话、找补、轻推),而不是发完就干等对方。
现在工具写死了:只有**最后一条是对方发的**才出建议 —— 见 [`copilot.py:139`](../copilot.py)
```python
if msgs and msgs[-1].get("sender") not in ("我", "系统", "unknown"):
```
所以「截图里最后一条是我发的」→ 直接 0 建议,返回「最后一条不是对方发的,不出建议」。用户希望:**即使截图停在我自己说话结尾,也能建议要不要再发点什么 —— 除非真没话说了。**

### 核心判断(本功能的灵魂)
**最有价值、也最危险的不是「生成追加文本」,而是「判断这时候该不该闭嘴」。**
造句容易;难的是工具敢说「这里别追,把球留给对方」。这直接顶在产品的「**不舔 / 点到为止 / 推拉**」卖点上 —— 若变成「你一发完就怂恿你再补一句」,等于在教用户连环夺命 call,反砸差异点。
所以「除非真没话说了」不是边角,而是**主逻辑**:默认先掂量「值不值得追」,**只有真有增量才给文本**。

### 追加的类型(意图不同,不可一锅烩)
| 类型 | 场景 |
|---|---|
| 补充/澄清 | 刚发的话有歧义或没说完 |
| 递进 | 顺自己话题再递一层(抛钩子/延伸) |
| 轻推(沉默后) | 对方久没回,低压力带价值的一句(**不是**「在吗」) |
| 收尾/给台阶 | 话聊到头,自然收一句留口子 |
| 救场 | 上一句发崩了,找补 |

### 时间维度的限制(要如实承认)
- 「刚发完顺手补一句」 vs 「对方久没回该不该推」是两件事。
- 后者需要知道**距上次多久**,但**单张截图里没有时间信息**。
- ⇒ 「沉默后轻推」要么靠手动触发,要么以后做**时间感知**(较重)。先做即时补充更稳。

### 落地设计(不动红线,仍 copilot/只出草稿/永不自动发)
1. 改 [`copilot.py:139`](../copilot.py) 的门:最后一条是「我」→ 进**追加分支**(而非直接不出建议)。
2. 新增 `agent.draft_followup()`(对照 `draft_reply`):prompt 先做「值不值得追」判断 —— **要么给追加候选,要么明确「先别发 + 理由」**。
3. 复用军师层 `assess_stage` 做火候校准:低阶段基本不追,关系越稳越敢补/双发。
4. UI:追加候选标「**追加 · 可发可不发**」;该闭嘴时把「建议先不发 + 理由」放显眼处,绝不让人觉得工具永远在催多发。
5. 监控模式不变:`peek` 只在**对方**发新消息时触发,所以追加天然是**手动**「我想再补一句」动作,工具不会自己冒出来催(这反而对)。

### 待拍板的开放问题
- **默认姿态**:进分支时默认偏「先给追加候选」还是默认偏「先劝别追,除非真有增量」?(倾向后者,更贴不舔定位)
- **沉默后轻推**现在就做(需时间感知,重)还是先只做「刚发完的即时补充」?
- **触发方式**:自动检测最后一条是我就出追加,还是给个按钮「想追一句?」按需触发?

### 验收设想
- 最后一条=我、且确有增量(话没说完/可自然递进)→ 给 1~2 条克制的追加,且区分类型。
- 最后一条=我、但追加只会显得需要/掉价 → **明确建议「先别发」并给理由**,不硬凑文本。
- 阶段低(L0–L1)时整体偏向「别追」。
- 全程不自动发,仅草稿。

## F2. DeepSeek token 成本优化:前缀缓存 + 军师判定门控

**状态**:🚧 进行中 —— 步骤 1(用量计量)✅ + 步骤 2(军师判定门控)✅ 已完成并验证;步骤 3-4 待做

### 背景 / 痛点
前置 prompt 很长,DeepSeek 每次读取吃很多 input token。**重要前提:这套 prompt 当年是按本地 7B(Ollama)脾气调的,现在主力是 DeepSeek,约束变了。**

真实成本结构(一次「读取」= **4 次 DeepSeek 调用**,见 [`copilot.py:132-150`](../copilot.py)):
| 调用 | 次数 | system 里的重料 |
|---|---|---|
| `assess_stage` 军师判定 | 1 | `_lovehelper_block` + `_STAGE_RUBRIC`(~800字)+ 记忆 |
| `draft_reply` | **×3 人设** | `_ROLE` + `_lovehelper_block(含 playbook)` + 人设 + 判定 + 手动上下文 + 记忆 + `_RULES` |

⇒ 最重的 LoveHelper 方法论 + playbook,一次读取里被重发 ~4 遍。

### 两条优化线(拆开,ROI 不同)

**① 前缀缓存(用户说的「像 cache 命中区域」)**
- DeepSeek API **自动对相同前缀磁盘缓存**,命中部分按约 1/10 计费,无需像 Anthropic 那样手打 `cache_control`(对比:[`llm.py:92`](../llm.py) Anthropic 路径打了标记,[`llm.py:118` `_deepseek`](../llm.py) 没打,但 DeepSeek 自动)。
- **命中要靠前缀逐字节相同**。现状 [`agent.py:231`](../agent.py)「人设最前、`_RULES` 压轴」,而 `_RULES` 前面是会变的记忆/手动上下文 → 这段静态硬规则**永远缓存不到**。7B 时代「开头结尾最敏感」的理由在 DeepSeek 上不成立。
  - 改法:**所有静态文本(ROLE/lovehelper/playbook/RULES/阶段口径)挪到最前拼成固定块,所有易变(人设/判定/记忆/当前对话)压到最后** → 缓存前缀拉到最长。
- **先打用量日志**:[`_deepseek`](../llm.py) 把返回的 `usage`(含 `prompt_cache_hit_tokens`/`miss_tokens`)扔了 → 落盘,先看清缓存命中率和钱花在哪,**别蒙眼优化**。

**② 军师判定门控(用户说的「分数不常变、检测到才更新」)**
- 澄清:**记忆更新已是手动**(只在「导入历史」`distill_memory` 跑,非每读取)。每次读取真正在重算的是 **`assess_stage`(关系分数),每读取全量打一次**([`copilot.py:132`](../copilot.py))。
- 关系分数是**慢变量** → 缓存进该联系人记忆,平时复用;只有**廉价触发器**判断「这轮可能动分」才重跑。
- 触发器用**免费启发式**(不再打模型,否则没省):对方新增 ≥N 条 / 命中「分数事件」关键词(约/见面/喜欢/在一起/别烦我…)/ 手动「重新判定」按钮。标准**缓存 + 失效**模式。
- **附带好处**:现在分数每读取重算会抖(模型随机性),缓存 + 慢更新后**又便宜又稳**,提升军师可信度。

### 其它可改
| 项 | 说明 | 风险 |
|---|---|---|
| 3 草稿 = 3 次全量调用 | 可合成 1 次「三种风格」;但故意分开调求多样性。**缓存命中后第 2/3 次重前缀≈1/10**,可能不必合并 | 合并掉多样性 |
| `thinking` 别开 | [默认 disabled](../llm.py) ✅,核对本地配置;开 reasoning 翻几倍 token | 已规避 |
| 记忆压实 | 记忆每读取发 4 遍;用上 `compact_memory`(≤30字/条)、别让记忆无限长 | 低 |
| distill 降档 | 历史导入一次性多调用,可走更便宜模型/更低 effort | 低 |

### 优先级
1. ✅ **打用量日志**(`usage` 落盘)—— 已完成:`llm` 计量 + `copilot._log_tokens` 落
   `usage.json`/`token_usage.log` + 控制台一行。实测确认 DeepSeek 自动前缀缓存生效(次调 67% 命中)。
2. ✅ **gate 掉每读取的 `assess_stage`** —— 已完成:`_staged_analysis` 缓存 + 启发式触发器
   (对方新增≥4 / 分数关键词)+ 手动「重新判定」按钮 + `/api/reassess`。实测第二次读取 0 调用。
3. ⏳ **prompt 重排「静态在前、易变在后」** —— 吃满自动缓存,低风险。**下一步**。
4. ⏳ 3-草稿是否合并、distill 降档 —— 攒几次真实 `token_usage.log` 再决定。

### 待拍板

### 验收设想
- 一次读取的 DeepSeek input token(尤其 cache-miss 部分)较优化前显著下降,且能在日志看到命中率。
- 多数读取不再触发 `assess_stage`(分数复用缓存);分数事件发生时能正确重判。
- 回复质量/多样性不退化(改排序、加门控后人工对比几轮)。
