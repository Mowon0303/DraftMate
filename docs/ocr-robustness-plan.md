## 已查明(避免重复踩坑)

- **个别字误读是 easyocr 识别上限,不是截图清晰度问题**(2026-06-22 实测)。整条 capture→OCR
  链路无任何降采样:`_win_grab` 按物理像素截图存无损 PNG,`_apply_crop` 只裁不缩,`ocr_easyocr`
  直接读全分辨率图;DraftMate 左侧预览看着糊只是网页 CSS 缩小显示,**不是 OCR 的输入**。
  合成实验:「诶」在 20/26px、`mag_ratio=2`、2× 预放大、beamsearch、对比度强化、以及全部组合
  下**一律**被读成 谈/埃 —— 放大/增清晰度救不回来。「客人」等其它字均正确(印证截图里的
  「卡尔」是微信原文、非误读)。
  - **唯一真·accuracy 杠杆 = 换更强引擎**(代码已支持 `ocr_backend: paddleocr`,中文普遍强于
    easyocr);但 paddle 安装重(数百 MB,装进 D: venv 不占紧张的 C:)。待用户判断值不值得。
  - 现状可接受:单字噪声基本不影响结果(DeepSeek 能理解「谈哟/误哟」,回复照常正常),且
    低置信度 ⚠️ 警告已会提示核对。

## 已完成(归档)

- **第一轮(0f1f3f4)**:`detect_avatars` / `_content_mask` / 图片消息检测的尺度从固定窗口比例(`H//160`、`0.03–0.16H`、`0.04/0.13H`)改为锚定文字行中位高 `mh`;content mask 无条件计算;系统消息加 `_looks_system_text` 正信号门槛(M3)。新增 `tools/ocr_geometry_harness.py`,3 尺度 × 明暗主题全矩阵 PASS。对应审计项 **L1 / M1(部分)/ M3**。
